# Cleo 记忆系统项目研究

## 结论

Cleo 当前最适合借鉴的是“有界的 Markdown 当前记忆 + 独立的历史查询”，而不是增加一套与 Markdown 内容相同的 JSON 记忆库。推荐以 Hermes 的写入容量约束为基础，借鉴 Claude Code 的文件可读性、Letta 的普通文件查找，以及 Hindsight 的局部更新和新鲜度标记。数据库型系统适合作为边界对照，不宜直接引入。

JSON 不会因为格式本身导致无限增长，也不会因为称为“小型文件”就自动保持小。若每次只替换有限内容，它可以有界；若持续追加候选、证据、快照和版本，它仍然会膨胀。将同一份偏好正文同时保存在 JSON 与 Markdown 中，虽然可以设计成规范数据与投影，但对当前需求没有显著到足以承担同步成本的收益。

应分别约束三种规模：当前有效记忆、每次注入模型的上下文、持久化总数据。只限制前两者不能承诺总磁盘空间不再增长。原始会话若永久保留，磁盘仍随使用增长；这属于历史保留政策，不应通过偷偷删历史或多生成几层摘要解决。

本报告基于截至 2026-09-09 可访问的官方文档，并对 Hermes、Mem0、Graphiti 的相关源码固定提交核对。项目的使用广度不等于记忆效果已被证明；未在 Cleo 上实测的收益均视为待验证判断。

## 一、如何判断一个设计是否适合 Cleo

本次比较采用以下约束：MEMORY.md 只记录用户偏好，允许最多一个手动整理时的状态快照；不以本地 sentence-transformer 为依赖；不急于选择语义模型；避免把杂乱事实从 Markdown 搬到另一种容器继续积累。

此外，Cleo 同时连接聊天与多个生产力 harness。适用的设计必须能解释并发会话、跨项目范围、人工编辑和历史恢复，不能假设只有一个 agent 永远独占一个文件。

| 维度 | 真正需要核对的内容 | 容易误判的表述 |
| --- | --- | --- |
| 唯一正文 | 哪一份内容被视为当前有效记忆 | “都有 JSON 和 Markdown，所以一定重复” |
| 写入增长 | 达到容量后拒绝、替换、合并，还是继续追加 | “最多加载 200 行，所以存储有界” |
| 纠正 | 改旧条目还是新增一条相反的条目 | “语义去重等于过期处理” |
| 历史 | 能否回到原始来源；原文是否仍在 | “摘要有引用就一定正确” |
| 语义处理 | 提取、筛选、纠错、召回、重排分别由谁完成 | “有 embedding 就懂用户” |
| 运行成本 | 新增模型、服务、索引、维护和失败处理 | “本地文件等于零复杂度” |

## 二、七个项目的机制对照

| 项目 / 子系统 | 当前有效内容的载体 | 容量和历史机制 | 对 Cleo 的适配判断 |
| --- | --- | --- | --- |
| Hermes 内置记忆 | MEMORY.md / USER.md | 工具写入硬上限，支持替换与删除；历史另查 | 最接近；仅取其偏好与容量机制 [1–4] |
| Claude Code 自动记忆 | MEMORY.md 与主题文件 | 入口加载有界；未证明整个记忆目录硬封顶 | 文件方式适合，扩展事实目录不适合 [5] |
| Letta MemFS | Git 管理的记忆仓库和 Markdown 工作副本 | 常驻与按需分层、版本历史、doctor | 借鉴文件读写与局部维护，不照搬全部平台 [6–7] |
| OpenClaw 内置记忆 | Markdown 正文 + SQLite 索引和其他状态 | 分层、替代标记、后台整理；总量仍需维护 | 借鉴职责分离，不照搬多层增长 [8–10] |
| Mem0 当前 OSS | 向量库中的结构化条目 | 当前 add 为追加式；另有 update/delete | 不符合取消事实库的目标 [11–12] |
| Graphiti | 时间知识图谱及来源 episodes | 新事实使旧关系失效，历史仍保留 | 只借鉴时间语义，不引入图基础设施 [13–15] |
| Hindsight | facts、observations、mental models | 分层推导、定向刷新、来源与版本 | 借鉴刷新机制，不引入全部事实层 [16–17] |

表中的适配判断是基于 Cleo 目标作出的分析，不是各项目总体质量排名。所有项目都有偏离 Cleo 需求的部分；没有发现可以原样搬入、同时满足全部限制的现成系统。

### 1. Hermes：最值得学习的是硬预算与编辑语义

Hermes 的内置记忆直接保存在两个 Markdown 文件中：MEMORY.md 用于 agent 笔记，USER.md 用于用户信息。官方默认分别为 2,200 和 1,375 字符。文件加载为会话启动时的固定上下文，memory 工具提供 add、replace、remove。[1]

固定提交的 MemoryStore 源码确认：新增和替换均检查最终字符数，超限返回错误；批处理先在内存执行全部操作，再检查最终预算，失败不写入。写文件使用锁、重新读取和原子替换。因此它的容量限制确实作用于工具写入，不只是提示词中的建议。[2]

源码中对正文的读取与保存直接操作 Markdown；工具返回 JSON 是调用协议，不等于另存一份 JSON 正文。内存中的启动快照也不是第二个持久化真相。历史查询走独立的 SQLite 会话搜索，当前实现可看到 FTS5 和按会话谱系去重。[2–4]

适合 Cleo 的部分是：正文一份、每次写入受硬预算约束、同义内容应合并、变更应替换、整批失败不污染旧文件。其内置记忆也允许环境事实和完成事项，内容策略不能照搬。官方还警告多个进程不应随意共用同一个 Hermes home；Cleo 必须保留自己的并发协调。[1–2]

限制：工具限额不能阻止人工或任意 shell 直接写超大文件，Cleo 的加载入口也需要检查。容量有限不能保证内容正确；让模型为了塞入新内容自行删除旧内容仍可能伤害偏好。因此“超限拒绝”值得借鉴，“自主删掉不重要偏好”需要另行决定。

### 2. Claude Code：单一文件内容与小入口，不是全库容量保证

Claude Code 将人工规则与自动记忆区分。自动记忆目录有 MEMORY.md 和主题文件；启动只加载入口前 200 行或 25KB，详细文件按需读取。文件可以直接编辑或删除。[5]

这里的小入口解决上下文成本，不能证明磁盘中的内容不会继续增长。把较长笔记移到更多主题文件，可以让入口短，却仍可能形成越来越大的事实集合。

对 Cleo，适合借鉴的是 Markdown 可读可编辑、当前需要的信息才读取，以及内容范围的明确区分。Cleo 不应直接采用“入口列索引，后台再写很多事实主题文件”的扩展方式，否则只是把 17214 的杂乱记忆拆成更多文件。

文档能够证明上述公开行为，但本次没有 Claude Code 内部写入实现的源码证据，也没有证据表明它对整个自动记忆目录强制实施总容量或可靠的语义纠错。不能由“产品成熟”推导这些保证。

### 3. Letta MemFS：文件就是工作界面，语义索引可选

Letta 当前文档把 MemFS 定义为 Git 支持的记忆仓库，并在运行机器上投射为工作副本。system 目录内容常驻上下文，其他文件按需读取；默认不含语义或向量索引，agent 可使用普通文件搜索。对话历史搜索是另一个子系统。[6]

后台 Dreaming 会回顾对话并更新记忆，另可启用第二个后台会话审查修改；doctor 检查布局、重复和上下文消耗。[7]

这说明“让模型阅读并编辑有限的记忆文件”本身是一条实际采用的路线，无须先建 embedding 管线。对 Cleo，更合理的借鉴是普通文件读写和在既有内容上修改。

但文件树、参考文件和 Git 历史仍可增长；分层不是总量封顶。云端仓库与本地工作副本是同步副本，不等于两套各自生成的偏好正文。Cleo 暂时不需要引入云同步、完整 MemFS、独立 Git 工作树编排或自动生成技能。

也不能从 Letta 提供可选复核直接得出 Cleo 必须两模型审核。其效果、费用和等待时间需要在同一组 Cleo 对话上比较。

### 4. OpenClaw：正文、索引和来源状态确有不同职责

OpenClaw 把用户模型、长期记忆、日常记录分开。USER.md 中的偏好带观察时间和 active/superseded 标记，偏好改变时更新对应位置，避免到处出现相反的有效要求。[8–9]

其内置引擎对 Markdown 建索引，但 SQLite 也拥有独立来源元数据，当前还与会话等持久状态共处一个 agent 数据库。不能把整个 SQLite 文件称为可删除缓存；官方明确说明重建记忆索引不能恢复被删除的会话历史。[10]

这给 Cleo 两个启发：一是文件之外确实可以存在有价值的运行元数据，但不必重复保存偏好正文；二是去数据库必须按表和职责判断，不能按扩展名一刀切。

不过，OpenClaw 的日常笔记、Dream Diary、索引、来源和后台提升组成了比 Cleo 当前目标更宽的系统。旧偏好留在当前文档并标 superseded 也会占空间；Cleo 可考虑只呈现当前有效值，过去值留在既有历史里。

OpenClaw 文档的不同页面更新速度不一致：概览与引擎页面对于可选后端的描述并不完全同步。本报告不据此确定 Cleo 的 provider 或部署选择，只使用明确的正文、索引和替代机制。

### 5. Mem0：有更新 API，不意味着 add 自动维护单一当前真相

当前官方 add 文档明确描述追加式存储。固定提交的 OSS 主流程会先检索相近旧记忆，将其送入 ADDITIVE_EXTRACTION_PROMPT，再对提取结果生成 embedding，做 hash 去重并写入新记录。update 和 delete 是另有的操作入口。[11–12]

这是需要注意的版本变化：过去常见的介绍把 ADD/UPDATE/DELETE/NONE 描述为自动统一管线，不能直接套用到本次核对版本。代码的部分说明字符串仍保留旧式措辞，应以实际调用路径和当前文档为准。[12]

Mem0 更适合需要大量可查询用户事实、结构化过滤和服务化接入的产品。它并不是为了把一个个人助手的偏好压到固定几条而设计。其附加的实体索引、历史和向量数据也不会因只返回少量搜索结果而停止增长。

对 Cleo，值得学习的是独立更新与删除的 API 契约；不建议当前引入其事实提取和向量存储作为核心。

### 6. Graphiti：真正区分重复、冲突和时间，但代价是保留更多结构

Graphiti 以 episodes 为来源构建实体关系图，保留时间有效区间。旧事实被判定失效后仍留在图中，以支持“当时是什么情况”类问题；其混合检索结合关键词、语义和图关系。[13]

固定提交的 dedupe_edges prompt 分别返回重复与冲突候选，明确不同日期、数值或限定条件不能简单认作重复。edge_operations 再结合时间区间处理 invalid_at 和 expired_at。因此它不只依赖向量相似度决定真假，也不是仅把最后写入的记录当最新事实。[14–15]

这是可靠性方向上的重要借鉴，但对 Cleo 来说不值得引入完整图谱。为了保存少量偏好而维护实体、关系、时间索引和图数据库，会扩大系统职责。更小的迁移单位是：修改偏好时明确判断“同义、纠正、局部例外、不相关”，状态快照注明证据截止时间。

Graphiti 的失效管理主要解决历史语义，不等于减少存储；保留所有过去关系正是它的功能。Cleo 若不需要通用时间知识图谱，就不应为一个轻量交接快照承担这套成本。

### 7. Hindsight：局部刷新与新鲜度值得借鉴，底层事实层不适合

Hindsight 的 retain 会抽取事实、经验并形成检索索引；随后可归纳 observations。Mental model 是围绕指定问题维护的文档，具备自身范围和刷新机制。[16–17]

它会标记相关底层信息是否发生变化，并支持增量刷新已有文档，避免每次整篇生成造成措辞漂移；同时保留来源和版本历史。[17]

对 Cleo 最值得借鉴的是：未变化的偏好文本不反复重写；状态快照一旦落后于后续事件就标记过期。无需为这两个行为引入 facts → observations → mental models 的完整系统。

其多层内容不是简单同文复制，而是不同抽象层。但抽象层不同并不意味着对 Cleo 有收益；每层都有生成、更新、验证和存储成本。当前恰恰应避免把单一偏好文件扩张成多层用户建模平台。

## 三、为什么 JSON + Markdown 在这里不划算

可以把多份数据分成三种情形：

1. **同一正文的两种持久化表示**：JSON 含完整偏好，Markdown 重新渲染同样内容。可实现，但编辑入口、冲突和恢复都必须处理。当前不推荐。
2. **正文与必要元数据**：Markdown 保存偏好，运行状态只保存处理游标、来源位置和文件版本。职责不同，有需要时可以保留。
3. **正文与派生索引**：为查找长历史创建关键词或向量索引。属于性能措施，应能标识源版本并按职责重建，不能自然升级为另一份权威事实。

之前“小型 JSON”提案的问题是没有给出必须复制正文的产品理由，也没有把来源和修订的增长计算进去。即使规范数据有 20 条上限，证据列表、快照历史、删除记录和中间候选仍可能线性增长。

推荐的新方向是：MEMORY.md 成为当前偏好内容的唯一持久化正文；UI 和 agent 都读取、修改它，不由另一个内容库随时覆盖。若需要少量来源，可以使用同文件的短注释或现有会话元数据中的指针，不复制原文，也不先建一套万能审计库。

这个选择仍有代价：自由 Markdown 不如严格 JSON 易于字段验证。可以约定少量标题与条目边界，由程序解析并校验，不需要赋予 agent 任意扩展章节的权利。工具用 JSON 请求修改操作是正常协议，这与保存第二份 JSON 内容是两回事。

## 四、如何真正限制增长

### 当前记忆预算必须发生在写入前

仅在 prompt 中要求“保持简洁”不足以防止膨胀。应在程序发布前检查完整候选文件，包括元数据和可选状态；超限不发布，旧文件保持有效。修改也受限，不能只限制 add。

对中文不能直接照搬 Hermes 的英语字符与 token 近似值。第一版可以选择一个明确字符/字节上限，并对实际注入做代理 token 计数；预算数字留待 17214 预览后确定，不为好看先锁定 1,200 tokens 或 20 条。

### 容量满了不能自动溢出到其他文件

如果 MEMORY.md 超限后自动生成 preferences-2.md、archive.json 或 facts.sqlite，当前问题会原样回来。优先同义合并、用新值替换旧值；无法无歧义缩短时，拒绝新增并让 UI 显示未保存，而不是静默牺牲用户明确要求。

每个 scope 的文件有界仍不等于全局恒定大小。假设有 P 个实际项目，每个预算为 B，则当前偏好总量大致随 P × B 增长；应禁止 agent 为逃避预算自动创建 scope，并设置单次跨 scope 注入预算。全局偏好不能复制进每个项目。

### 状态只有一个版本进入当前文件

如果保留状态，应只占一个小节，明确工作项、来源会话与证据截止时间。旧“测试还没跑”和新“测试已通过”不再同时存在于当前状态。过去的过程留在原始事件历史。

17214 有多个课程子任务，最后整理的 HW1 状态不能成为 Lab 2 的状态。可以在范围匹配时才注入该小节；状态如何选定、是否干脆不放 MEMORY.md，仍是待审查产品选择。

### 中间处理与历史分别管理

恢复文件可保存尚未完成的处理进度，但成功后不能永久累积每块候选或整篇旧 Markdown。审计若确有需要，应优先利用已有事件与版本机制，而非每次制作新备份文件。

原始会话是另一种增长：保留它才能查询过去，也意味着磁盘不可能绝对不增长。未来可以单独审查归档或删除策略，但这次不应以“避免记忆爆炸”为名删除用户历史。

## 五、语义判断在哪里发生：先拆开，再决定

| 任务 | 项目中的实际用法 | Cleo 是否现在必须加入 |
| --- | --- | --- |
| 判断什么值得保存 | Hermes/Claude/Letta 的 agent 在阅读上下文时决定记忆修改 | 整理过程已有模型；未必需要另设 gate |
| 判断同义、纠正、例外 | Graphiti 有显式 LLM 冲突判定；文件型系统可由 agent 编辑时判断 | 需要解决行为，但实现方式待比较 |
| 找相近的历史 | Mem0 用 embedding；Letta 默认文件查找；Hermes 内置历史可用 FTS5 | 本地 transformer 不是必需条件 |
| 对候选重新排序 | 独立 reranker 或 agent 阅读候选 | 等真实漏召回数据再决定 |
| 验证来源是否支持结论 | Letta 有可选后台审查；Cleo 先前提案设想独立复核 | 不是所有成熟系统的必选项 |

这里的重要区别是“没有独立语义模型”并不等于“没有语义理解”。让当前模型读完十条偏好后提出替换，已经使用了语义能力；是否再调用一个模型复核，是成本和可靠性之间的另一个选择。

以下三个实验可以保持同一存储设计，只比较决策路径：

- **单次编辑**：整理模型读取新证据与当前 Markdown，返回最小修改。
- **候选与合并分步**：前一步提出候选，后一步只处理去重、范围和纠正。
- **编辑后独立复核**：对最终少量变更及原始证据重新判断。

这三条都可以不使用本地 sentence-transformer。需要先比较错记、漏记、无谓改写和调用成本，不必现在决定远端 reranker、embedding provider 或固定双模型架构。

近期一篇预印本发现，其测试环境中的反复 LLM 归纳可能使记忆收益下降，原始经历保留仍有竞争力。这支持谨慎对待自动频繁重写，但实验不能证明“所有长期记忆无效”，也不能代替 Cleo 偏好与课程任务评测。[18]

## 六、对 Cleo 的适配选择

### 建议优先形成的约束

- 当前偏好正文只有一份，优先 Markdown；撤回 JSON 正文加 Markdown 投影的推荐。
- 不再生成独立的自动原子事实库，也不把它转存成散落的 Markdown 主题文件。
- 写入有硬预算，批量替换原子提交；不变的偏好不重写。
- 历史工具继续直接查可追溯的会话材料；索引与事实库明确区分。
- 偏好按适用范围更新；当前用户请求可以覆盖旧偏好。
- 状态若保留，只是一份有时间、有工作项的交接快照。
- 不为每个新事件自动扩写人格、知识图谱或多层摘要。

以上是研究后的推荐约束，尚未授权实施。全局偏好布局、persona 的处理、状态位置、预算大小、自动触发时机以及是否独立语义复核仍待审查。

### 三种存储路线

| 路线 | 优点 | 代价 | 建议 |
| --- | --- | --- | --- |
| 单一 MEMORY.md + 已有历史 | 直接编辑、无正文同步、容易理解增长边界 | 需小型格式约定与并发写入检查 | 优先 |
| Markdown + 独立 provenance 元数据 | 便于逐条来源展示，不重复正文 | 元数据仍需上限、编辑后可能失配 | 仅确有来源管理需求时增加 |
| JSON/DB 权威正文 + Markdown 投影 | 易做强 schema、查询、复杂 UI | 两种持久表示、再生成和迁移成本 | 当前无充分理由 |

第一条仍可以保留必要的 dream 游标和会话索引，不应把“正文一份”解释成“整个系统只能存在一个文件”。JSON 工具参数、临时内存对象和规范运行状态也不需要为了格式纯粹性去掉。

### 需要防住的三个具体回归

**人工编辑被覆盖。** 用户手改 MEMORY.md 后，下一次整理必须读取现有文件并验证基线；不从旧 JSON 重新生成。锁或文件 hash 可解决并发覆盖，但不保证模型的语义合并正确。

**删除的偏好复活。** 单纯删除正文不能承诺在全历史重跑后永不再提取。应优先增量处理；明确“以后不要记这件事”的请求需要被保存为可执行的删除/抑制意图，具体记录方式仍待设计。不能以省掉元数据为由隐瞒这一代价。

**为了压缩而丢掉用户意图。** 硬上限拒绝新写入比静默替换不明确的旧偏好更可控。若缩短确实改变适用范围或例外，应当不发布该修改，而不是把它算成成功压缩。

## 七、下一步应验证什么

先在 17214 的真实历史上离线生成三组预览：仅偏好、偏好加单个状态、偏好加有限来源标记。不改真实数据。比较哪种更易读、能否解释来源、是否出现重复和过期内容。

对语义路径使用同一组标注案例：稳定偏好、一次性要求、同义重复、明确纠正、局部例外、失败后通过、实施后回退、跨子任务、删除后重跑、人工编辑和并发整理。记录每一次错误的原始证据，不能把上一版模型摘要当标准答案。

容量测试不仅看最终 prompt：分别测当前文件大小、条目数、来源元数据、恢复文件、原始历史和索引。重复整理同一输入应不增长；没有偏好变化的会话不应增加偏好正文；超限修改应保持旧内容和清晰失败状态。

源码证据说明这些机制确实被实现，但本报告没有运行其他项目的完整测试套件，也没有测量它们在 Cleo 上的质量或性能。Claude Code、Letta、OpenClaw、Hindsight 部分主要依据公开文档，不把文档承诺当作完整实现审计。
