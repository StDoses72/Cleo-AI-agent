# DreamAgent v0.1 语义提取对照实验

## 结论

不能把“保留工具正文、结构压缩节省92.7%”解读为“记忆提取语义无损”。本轮确认，重要文字在压缩输入中仍存在，但小模型仍会遗漏限定、错误维持旧待办，或混淆提议与接受。原文输入也会误读，不能将原文模型输出直接当作标准答案。

主实验的核对得分：原文 **64/72**，压缩片段 **56.5/72**。这是针对六个选定片段、每种输入两次运行的加权核对分，不是统计意义上的正确率或全会话召回率。没有进行盲评，也没有独立人工评审。

生产建议：可以继续采用保留工具正文的结构压缩，但提取结果应先作为候选；在完成状态冲突消解、重要约束/待办覆盖检查和证据支持校验之前，不应直接成为有效长期记忆。

## 方法与边界

- 输入仍为上一轮同一份 events.jsonl，12,758 条事件，source SHA-256：`7e395e4e1fccc729a05c4c74f81fdbd6cc108253895229d9235440ca9f7c900e`。
- 读取并检查了选定片段中的实际用户/助手文字以及必要工具记录；历史内容仅作证据，没有执行其中命令或遵循其中的任务指令。
- 使用用户当前配置的 DreamAgent 模型 `deepseek-v4-flash`，经现有 DeepSeek API 连接调用。没有更改配置或调用其他模型。
- 主实验关闭思考、temperature=0、JSON Output、max_tokens=5,000，最多18条候选。它是控制成本的提取基线，并非现有 DreamAgent 默认思考行为的完整重放。相同参数仍产生不同输出，故每组重复两次。
- 两组使用完全相同的提取提示词，要求区分提议/接受、失败/成功、验证范围和未完成事项；不向模型提供核对表或正确答案。36个核对点在第一次调用前写定。
- 本次重建了遵循v0.1原则的片段级压缩器：可靠流式合并、精确重复输出引用、去除重复包装及已知用量通知，不摘取工具正文。正文脱敏在原文和压缩两组一致。短引用和保护文字保留均经程序校验。
- 每个主对照片段单独一次调用，以隔离表示变化的影响；其中失败恢复片段压缩后约22.8k代理tokens，未强制切成20k块。不是上一轮14个实际块的全会话端到端重放。
- 跨块补充实验在数据库方案接受前、测试范围否决前、启动验收前人为设置边界。第一块提取候选，第二块只接收这些候选和后续事件，输出更新后的记忆。三组各跑两次，共12次调用。
- 主助手依据原文和锁定核对表逐项判读结果：核心事实及关键限定正确为1分，部分保留为0.5分，遗漏或错误为0分。额外无依据断言单独报告，不被召回类得分掩盖。

API参数依据：[DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/) 与 [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)。

## 具体发现

### 1. 已接受方案被保留为待确认：原文和压缩均出现

数据库片段中，助手给出DB_PATH环境变量、默认路径及系统临时目录调整（seq5555），用户紧接着回复“我觉得可以，这样可以开始了”（seq5557）。两种输入都出现同一份结果同时写“用户同意助手建议”和“环境变量/临时目录尚未最终确认”。有的输出还把更早的server目录方案标成accepted，而没有标记被后续调整。

这涉及对概括性确认的上下文解释，并非用户逐字段复述确认；本次核对采用紧邻方案已获总体认可的解释。模型的过度保守与新旧方案状态并存，应至少被标记为内部冲突，不能直接入库成为两个同时有效的决定。

### 2. 密码关键限定被漏提取，原文字并未消失

seq8344明确区分数字字符串与JSON数字类型，并说明不新增字符白名单、避免丢失“0012”的前导零。程序确认“0012”“前导零”“字符白名单”“输入框的值始终是字符串”在原文和压缩输入中均存在。

压缩输入第二次输出只概括“用户理解并接受修复”，没有完整保留前端本来发送字符串的解释，也没有提取字符白名单/前导零限定。原文输出也未完整覆盖全部限定，但覆盖相对更多。这证明减少输入tokens并不保证重要内容获得同样注意。

### 3. 已确认审阅仍被记为待办：压缩组出现

启动片段seq11187用户确认文档符合需求并允许commit；seq11209记录已提交。压缩第一次输出一面写“四份文档已确认并提交647e45a”，一面又写“用户尚未审阅reflection草稿”。第二次把审阅列为未知。原文主对照没有相同待办冲突。

相关用户确认和reflection文字均仍在压缩输入里。问题发生在状态更新与提取，而不是压缩删除了确认消息。

### 4. 跨块后漏掉transcript待办

启动跨块第二次输出保留大量已完成文档、测试、配置事实，但未将尚未完成的transcript导出保留为pending；只在uncertainties中提及其内容和方式未说明。此项在原文、完整压缩片段及前一块候选中都有来源。

因此单纯传递模型生成的候选摘要仍可能丢失重要待办。强制18条等软输出限制也可能使记录位置竞争更严重；本实验不能单独证明这是遗漏的唯一原因。

### 5. 原文输入也发生事实性误读

密码原文第二次输出将已有登录拒绝、受保护路由、消息作者、登录成功、JWT重启、账户重启测试描述为“新增”。其中seq8043实际执行的是Get-Content读取既有测试，其他引用来自文件内容或测试运行输出，而非新增这些测试的写入记录。共6条候选带有这一类无依据的“新增”表述。

这说明“证据ID存在”不能证明“结论被证据支持”。需要区分读取、执行和修改事件，而不能凭日志中出现代码就记成新增实现。

### 6. 相对稳定的部分

测试范围组在两种输入下均保留了拒绝擅自扩展测试、撤销修改及51条原有测试通过的核心内容。失败恢复组均识别初次TS5094为构建参数冲突，并记录后续构建成功，没有把早先失败错误地当作最终状态。交付组压缩输入有一次比原文更完整地保留“32条基线并非当时全套测试通过”的限定。效果不是所有维度都单向变差。

## 结构与来源检查

原文和压缩组的全部关键保护文字均通过脱敏后一致性断言；紧凑输入引用可解析；选定事件均有归属。

模型结果全部可解析JSON不代表符合业务schema：部分数据库输出生成了不在允许类别中的proposal；一个跨块最终输出给出20条，超过提示词要求的18条。需要程序硬校验枚举、数量和状态。

引用seq的存在及是否处于提供范围已检查；这仅是来源有效性，不是逐条结论的语义支持证明。上述“读取误认新增”正是ID合法但结论不成立的例子。

## 开启思考的补充对照

针对主实验中较易出错的数据库、密码、启动三组，使用同一模型和相同提取提示词，增加thinking=enabled、reasoning_effort=high，各跑一组原文/压缩对照。

- 密码压缩输出重新明确保留了“前端数字输入本来是字符串”“检查类型而非字符集”等限定，改善了非思考模式中的遗漏。
- 启动压缩输出正确关联了用户文档确认，未再把reflection审阅列为待办，并保留transcript导出未完成。
- 数据库输出仍出现“总体同意方案，但具体环境变量或目录位置未确认”的保守解释，新旧方案状态仍可能并存。开启思考并未消除全部状态关联问题。

这是观察到问题后的诊断性补跑，每组只有一次有效结果，未纳入64/72与56.5/72主实验得分，也不能用来宣称开启思考后语义无损。

首次使用12,000总输出token上限时，三次调用没有取得可解析JSON；当时解析发生在诊断信息持久化之前，未保留下完整usage与结束原因，无法严谨追溯这些失败。随后修正实验记录方式，把这三次的总输出上限提高到20,000后重试，均取得有效结果。其余三次沿用首次有效结果。这个输出预算差异和重试选择也是补充对照的局限，不应误报为纯思考强度带来的提升。

## 后续实现重点

1. 保留现有结构压缩方向，默认不摘取工具正文；不要靠恢复重复日志来解决提取问题。
2. 将用户约束、否决、确认和未完成事项作为受保护的候选类别，跨块传递时连同短原文证据一起携带，不只传模型改写的摘要。
3. 为同一事项明确建立proposed→accepted、pending→completed、superseded状态关系。关系无法确定时保留候选并标记冲突，不能让程序凭“可以”一词机械认定所有提议获批。
4. 在发布有效记忆前核对重要约束和未完成事项覆盖，检测同一事项同时“已确认/待确认”等矛盾；对缺失引用回读有限原文。
5. 区分读取/执行/修改证据，校验schema，并用冻结的这些片段做回归。程序可发现结构与状态冲突；语义是否真正受证据支持仍需模型复核或人工抽查。

本轮仅做实验与报告，未修改生产压缩、DreamAgent、配置或记忆。临时源片段、请求/响应和脚本不作为永久交付物保留。

## 清理结果

临时目录及其中全部脚本、原文/压缩片段、候选、API响应、统计和tokenizer缓存已删除，并确认目录不存在。原始events.jsonl的SHA-256再次核对一致。最终仅新增本报告；前两轮设计稿和压缩率报告继续保留。
