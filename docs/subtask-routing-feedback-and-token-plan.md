# 子任务路由修订：内部排名、任务 token 与反馈闭环

日期：2026-10-21。状态：v2 实现已进入本地交付验证，具体使用入口见 [路由使用文档](benchmark-routing.md)。本文补充并修订[总架构计划](subtask-routing-architecture-plan.md)。按用户最新要求取消消耗预测，仅在两种 agent 模式的上下文侧栏增加当前任务累计实际 token。

## 1. 按用户设想调整后的流程

1. **确认候选。** 路由流程初始化时，宿主从当前连接、账号和真实 harness/runtime 目录生成可用模型集合，应用用户排除项。Evaluator 使用这份可信快照，不能自行声称另一个模型已连接。
2. **取得 AA 数据。** 将可用模型与 AA 成本、Intelligence/Coding/Agentic 等能力指标及速度资料关联。有有效缓存就复用；首次或过期时，按配置、访问级别和配额刷新。尽可能分页批量获取再本地筛选，不给每个模型单独发重复请求。无 key 或失败时使用有效旧快照或明确标注未知。
3. **建立内部排名。** 构建可解释的多维基线和各任务类型的候选顺序，附数据时间、匹配等级及缺失项。
4. **拆分并分配。** 主 agent 生成任务和验收标准，evaluator 结合排名、任务需要及用户偏好进行逐项分配。二者可以由同一模型在一次正常规划中承担，不强制多起一个模型；独立指定 evaluator 时，主 agent 保留最终任务边界和调度权。
5. **校验并执行。** 执行层复核实际选择，主 agent 决定并行和验收。记录全部协调、评估、执行与返工开销。
6. **收集反馈并更新。** 将用户修改、可信验收和返工与原任务及分配关联；先判断原因，再有界更新本地排序，使后续 evaluator 能看到变化及证据。

AA 是参考数据 API，接口提供能力、性能和价格字段；它不提供 Cleo 任务的成功率或“使用某模型一定会用多少 token”的预测。[官方字段与访问范围](https://artificialanalysis.ai/data-api/docs/reference)。

## 2. 排名：AA 基线与本地经验分开

内部不要只有一个不可解释的“模型总分”。保存三类信息：

| 层 | 内容 | 更新方式 |
|---|---|---|
| AA 基线 | 同评测口径内的能力分项、输入/输出价格、速度、延迟 | AA 刷新产生新快照；本地反馈不改它 |
| 本地表现 | 同类任务的可信验收结果、返工次数/开销、交接问题、耗时和用户评价 | 正常执行和反馈记录产生；可追溯和撤销 |
| 当前任务推荐 | 先满足硬约束，再结合任务类型、质量要求、成本/速度偏好与本地表现排序 | 每个 RoutingContext/任务批次生成，不能跨任务机械复用 |

同一模型可以在“文档整理”“复杂编码”“工具操作”中排名不同。能力、价格与速度并非同一单位，不直接把 AA Intelligence Index 减去美元价格；有可靠数据时展示各维度顺序与取舍。高能力且低成本的候选可优先，但缺失指标不视为零，也不把所有未知候选排成看似精确的总榜。

可比较范围必须携带评测族与版本。模型别名、推理档位及 runtime 版本不匹配时标明参考程度。AA API 价格与订阅实际支出分开；订阅仍有额度和资源开销。

新模型、新模型版本或新 harness 路径以 AA 和已知能力为起点，旧路径反馈只做明确标注的参考，不直接继承全部惩罚。模型“不支持”属于可用性门禁，不是能力排名下降；认证和网络问题也不应降低模型智慧排名。

## 3. 上下文侧栏能展示什么

### 3.1 当前代码具备的基础

`Inspector.tsx::ContextPanel` 已展示 `thread.usage`，`desktop/presenters.py` 和 runtime usage/event 链路已有输入、输出及部分上下文计数。它还不是整个路由任务的跨 agent 用量账本。

后续需明确 provider 的字段含义。当前部分展示路径会读取线程累计 `totalTokens` 并配合 context window 显示，不能未经核对就把它视为“当前上下文占用”。没有可靠窗口大小时显示未知，不能拿默认常量假装已知。

### 3.2 保留上下文占用，只新增一项任务用量

| 区域 | 要显示的内容 | 准确性要求 |
|---|---|---|
| 当前上下文（保留） | 当前主模型上下文占用、窗口上限 | 以 runtime 的真实语义为准；无法取得则未知 |
| 当前任务累计 token（新增） | 当前任务从创建至今所有轮次的已报告用量，包括关联子任务 | 两种 agent 模式均显示；只统计本任务，未上报不能当零 |

默认界面只增加一项“当前任务累计 token”。输入/输出和各参与者明细按需展开，不增加预测区间、默认模型对照或节省百分比。

缓存输入通常是输入 token 的子集，推理 token 是否包含在输出中按 provider 定义处理。不要把子集重复相加。跨 provider 的 token 单位可能使用不同 tokenizer，因此原始 token 汇总不能直接当成同等成本比较。

建议 UI 文案示意（以下全是设计示例，非本机实时数据）：

```text
当前上下文       15k / 200k
当前任务累计 token 37.2k（输入 29.1k / 输出 8.1k）
展开明细：
  主协调者        …
  evaluator       …
  Sonnet 子任务   …
  Sol 子任务      …
  Luna 子任务     …
  其中失败与返工  …（已包含在总数中，不再次相加）
```

### 3.3 统一用量账本

新增 `UsageLedger`，以当前任务会话为汇总根，使用 parent session、可选 plan、子任务、attempt、turn、provider 事件 ID 关联计数。保存 `reported` / `unknown` 和来源，原始 provider 计数与归一化计数可审计，不用估算补缺失项。

累计事件采用增量归一化；重复事件只计一次。进程恢复、线程复用、累计计数重置都要有边界记录。evaluator 与主模型复用时不能多算一个不存在的评估调用。取消、失败前已消耗的用量不能被丢弃。

有未报告项时写“已报告至少 X；另有 N 次调用用量未知”，而不是用零补齐或宣称已知完整总量。数据覆盖情况随账本一起返回 UI。

## 4. 两种 agent 模式采用相同口径

| 模式 | 当前任务累计 token 的范围 |
|---|---|
| 指定已连接的 harness | 当前任务内所有轮次、失败/取消前已上报的消耗和返工；切换模型后继续累计 |
| 子任务路由 | 主 agent、独立 evaluator、所有关联子任务与 attempt 的用量；失败、取消和返工均计入，复用的评估不重复算 |

“当前任务”按会话内的目标分段：evaluator 判断新目标时开始新账本，追问和返工继续累计；不是全 session 或全账号用量。历史保留，在同一任务里切换两种模式不清零。具体实现与迁移规则见 [任务用量账本](task-token-ledger.md)。

取消默认模型 token 预测、估算器、基准模型选择及其数据字段。读取和显示账本不调用模型；开启会话内任务划分后，后续用户消息会额外调用已配置 evaluator 判断边界，其实际用量也计入。缺失用量不估算补齐，边界判断不改变 AA 排名。

## 5. 用户反复修改如何变成 evaluator 的反馈

### 5.1 将后续对话关联到具体任务

主 agent/宿主记录 `decision_id → task_id → attempt_id → artifact/check → feedback`。用户继续修改同一产物时关联原任务；新增目标时建立任务修订或新子任务。

同时提供轻量反馈选项：“仍未解决”“符合预期”“这是新增需求”，并允许用户改正自动关联。普通聊天不必每次弹问卷。

“反复添加对话”是复核信号，单独的消息数量不能证明执行模型失败。区分：

| 观察 | 建议归因 | 对排名的作用 |
|---|---|---|
| 用户反复指出同一验收要求未达到，或同一可信测试持续失败 | 原任务执行/选模可能不适合；还须检查上下文交接 | 更新该任务类型/执行组合的返工和失败证据，提示本次重新评估 |
| 三个子任务各自通过，但组合结果不完整 | 拆分、依赖或整体验收设计问题 | 更新协调/拆分策略提示，不给三个 worker 一起降能力排名 |
| 主 agent 没传必要文件、约束或前置结果 | 交接问题 | 更新上下文准备策略，不简单惩罚 worker |
| 用户在原成果上增加新功能或改变标准 | 新需求或需求变化 | 作为新工作记录，不能计入原模型失败 |
| 工具、认证、额度或网络故障 | 环境/可用性问题 | 更新连接健康或运行可靠性；不改智慧基线 |
| 多次补充但无法确定是否原要求未解决 | unknown | 留下待复核信号，暂不形成负面能力样本 |
| 明确满意或可信验收通过 | 正向结果 | 增加对应任务/配置的正向证据；agent 自述完成不够 |

### 5.2 分配到 Sonnet / Sol / Luna 的例子

假设三个子任务分别由 Sonnet、Sol、Luna 执行，用户随后三次指出 Sonnet 负责的同一个解析错误仍存在：

1. 把三条修复对话关联到同一任务 episode，记录返工 token、耗时和未通过的验收；不能把三条对话伪装成三个独立失败样本。
2. evaluator 获得“上次选择理由、必要上下文是否送达、失败证据、返工成本、可用替代项”，重新判断是模型选择、任务拆分还是执行问题。
3. 主 agent 决定补上下文、重新拆分或改用替代模型。换模型前仍检查已有改动与副作用，执行升级次数和预算限制。
4. 若归因支持选模不适合，降低该执行组合在相似任务上的本地优先级或提高风险提示；Sol 和 Luna 不因相邻任务失败受罚，AA 原始分数保持原样。
5. 如果后来确认是需求变化或工具故障，撤销错误归因，并重建受影响的本地排名修订。

### 5.3 更新机制

新增逻辑角色，不必都独立成服务：

```text
FeedbackCollector → OutcomeAttribution → RankingUpdater → RoutingContext
       ↑                                       ↓
  后续对话/验收                           evaluator 下次看到修正
```

- 主 agent 在正常返工过程中生成结构化归因，优先复用已有测试、产物和用户反馈；不为每条新消息额外调用一个评审模型。
- evaluator 可以提出归因建议，但不能直接覆写排名数据库。确定性 updater 校验关联、证据类型、作用域、重复事件及策略边界后产生修订。
- **立即反馈，渐进调整。** 一次明确失败立即进入证据记录并触发本次任务复核；少量或隐含信号主要提供临时风险提示。跨任务常规排序调整在积累独立、可归因结果后生效，不能因连续三条消息就全局永久降级。
- 初始工程参数建议：至少 5 个独立且有明确结果的同类任务后启用常规排序修正，局部经验对最终偏好的影响上限先设为 15%。这些是待离线检验的产品参数，不是统计上已校准的准确率或置信度保证。
- 排名按任务类型、模型版本、effort、harness/runtime 和必要上下文特征分范围；优先为当前用户/项目保留经验，不自动传播到无关项目。主协调者与 evaluator 的拆分/分配问题另记。
- 更新保留 old/new、原因、证据 ID、样本数和策略版本。支持冻结、撤销反馈、恢复 AA 基线；新模型版本不直接继承旧版全部修正。
- 学习质量/消耗偏好不能放宽权限、用户排除、预算或可用性约束，也不能自动训练模型、付费对照测试或更换 evaluator。

该机制是用户明确要求新增的“本地反馈更新排序”，已超出最早仅观察记录的第一版范围；实施时应作为显式功能策略，而不是隐蔽地改变原有路由。

## 6. 数据与模块增量

| 组件 | 主要输入/输出 | 优先复用位置 |
|---|---|---|
| RoutingContext 准备 | 可用候选 → AA 卡片、相对排名、修订摘要 | routing catalog/benchmarks |
| RankingStore | AA 基线与本地表现独立保存；读出任务相关排名 | routing 新模块，不复制 provider |
| Evaluator 决策 | task + context → assignment、理由与证据 | routing evaluator/execution |
| UsageLedger | 事件 → 可去重的实际用量及缺失信息 | harness events、desktop presenters、routing attempts |
| Feedback/RankingUpdater | 验收、返工、用户反馈 → 可撤销的局部排名修订 | sessions/events 与 routing records |
| ContextPanel | 保留上下文占用，新增当前任务累计实际 token；两种模式一致 | 现有 Inspector 上下文栏 |

## 7. 四批计划中的位置与验收

1. **第一批**：先统一可用性与模型身份，查清主模型标签及 runtime 差异。未经支持校验的模型不因 AA 排名高而进入执行集合。
2. **第二批**：实现候选确认 → 有界 AA 刷新/缓存 → 参考卡片与任务相关相对排名。使用本地 fixture 验证部分数据缺失、不匹配和成本类型差异。
3. **第三批**：evaluator 分配接入统一委派，同时建立任务 episode、反馈归因与有界 updater。验证新增需求不误罚、同一问题多次反馈去重、局部失败不污染其他 worker、撤销可恢复。
4. **第四批**：统一用量账本与上下文侧栏，在指定 harness 和子任务路由两种模式下显示当前任务累计实际 token，再做端到端离线交付验证。覆盖主/evaluator/worker/返工全计数、缓存与推理 token 不重复、累计事件恢复、未上报、模式切换及不同任务隔离；不实现消耗预测。

第一批完成不等于整个闭环已完成。实施期间保留旧规则策略可回滚，不自动重置用户主模型、评估器、连接或排除项。本次只更新方案与图，不开启反馈学习、不调用实际 AA 账号接口，也不进行真实模型推理。
